## Why the previous release did nothing

The earlier build published `build/tmp/deobfMcMCP/deobfed.jar` — the 11 MB
deobfuscated Minecraft listed above — under the release name. Its CI step globbed
for any jar and took the first match. That archive contains no Sky VeLor class, so
nothing in it could have worked. Two independent defects in the Beta-0.10.7v source
also guaranteed the feature would not work even had the right jar shipped:

1. **The mod never compiled.** `PekaClientMod.java` contained a literal
   two-character `\n` sequence where a newline belonged — a syntax error, so
   `compileJava` failed and there was no mod jar to package. `CustomItemRenderer`
   additionally declared `@Override` on `renderFireInFirstPerson(float)`, which is
   `private` in 1.8.9, and on `renderMapFirstPerson(float,float,float)`, which does
   not exist in 1.8.9 at all. Both were further compile errors.
2. **The renderer was installed where nothing reads it.** See below.

## The rendering defect, and the evidence that identified it

Minecraft 1.8.9 holds the first-person renderer in two places, and only one is on
the render path:

- `Minecraft.itemRenderer` — `private`, non-final. Only the constructor and the
  `getItemRenderer()` getter touch it.
- `EntityRenderer.itemRenderer` — `public final`, captured in the `EntityRenderer`
  constructor from `mcIn.getItemRenderer()`.

Every call goes through the second one. `EntityRenderer.updateCameraAndRender`
calls `this.itemRenderer.updateEquippedItem()`, and `renderHand` calls
`this.itemRenderer.renderItemInFirstPerson(partialTicks)` and then
`renderOverlays(partialTicks)`.

Beta-0.10.7v replaced `Minecraft.itemRenderer`. `EntityRenderer` had already
captured the vanilla instance at startup and kept drawing with it, so the slider
moved, the config saved, and the screen did not change. It also looked the field up
by the literal name `"itemRenderer"`, which does not exist in a reobfuscated
runtime, so the lookup threw and an empty `catch` block marked the feature
initialized anyway — hiding the failure.

These facts were established by decompiling the real 1.8.9 renderer in CI and by
`javap` on the deobfuscated Minecraft jar, rather than from memory. That decompiled
output is Mojang-derived, so it was used inside the build run and is gitignored; it
is not committed to this repository. The conclusions above are reproduced from
`javap` signatures, which are retained in the build logs of run 38897551904.

`FirstPersonItemSetup` now installs into the `EntityRenderer` field that is really
read, points `Minecraft`'s field at the same instance so both agree, finds both
fields **by declared type** rather than by name so it works identically in the
development workspace and the reobfuscated release, clears `final` once on Java 8,
reads the write back to confirm it took, retries from the client tick until
`EntityRenderer` exists, and logs instead of swallowing failures.

## Bytecode-level confirmation

Parsed from the shipped jar:

`CustomItemRenderer` — superclass `net/minecraft/client/renderer/ItemRenderer`,
declares:

| Declared method | Descriptor | Vanilla member |
|---|---|---|
| `func_78440_a` | `(F)V` | `renderItemInFirstPerson(float)` |
| `func_78441_a` | `()V` | `updateEquippedItem()` |

and calls `ItemRenderer.func_78440_a`, `ItemRenderer.func_78441_a`,
`CustomItemRenderer.func_78444_b` (`resetEquippedProgress`),
`GlStateManager.func_179094_E` / `func_179152_a` / `func_179121_F`
(`pushMatrix` / `scale` / `popMatrix`), and — the part that proves the GUI is wired
through — `FirstPersonItem.getItemScale()` **and**
`FirstPersonItem.getAnimationSpeed()`.

Because the overrides are declared under the SRG names that `EntityRenderer` calls
virtually, they bind in the obfuscated runtime. A deobfuscated development jar would
declare `renderItemInFirstPerson` instead and would never be invoked.

`FirstPersonItemSetup` — calls `Minecraft.func_71410_x()` (`getMinecraft`), reads
`Minecraft.field_71460_t` (`entityRenderer`) as a direct field, constructs
`CustomItemRenderer`, and uses `Class.getDeclaredFields`, `Field.getType`,
`Modifier.isFinal`, `Field.setAccessible`, `Field.get`, `Field.set`,
`Class.getDeclaredField("modifiers")` and `Field.setInt` — the whole type-based
lookup and install mechanism, correctly remapped.

## Automated tests

`tests/run-tests.sh` against the compiled classes and the real Forge/Minecraft
classpath: **24 suites, 3,345 checks passed, 0 failed**, exit 0.

`FirstPersonItemTests` (28 checks) is new and covers the values that reach the
renderer: both defaults resolve to an exact `1.0f` multiplier, which is what makes
the renderer skip its matrix work at 100%; a switch turned off forces the vanilla
value regardless of slider position; the percent-to-multiplier conversion; the clamp
bounds, which mirror the range the properties loader clamps with; and
reset-to-defaults.

`tools/verify_release_jar.py` adds **36 checks, exit 0** on the artifact: it is the
mod and not an intermediate, the version metadata is right, every expected class is
present (both the first-person renderer classes and the Terminal GUI classes from
the merged baseline), the deleted dead class is absent, the keybind labels are
packaged, nothing unrelated or nested was included, and Minecraft members are
referenced by SRG name with no development names left. Member names are read only
from `Fieldref`/`Methodref`/`InterfaceMethodref` constants, so the mod's own local
variables and methods cannot be mistaken for unmapped Minecraft members.

Reproduce with:

```sh
python3 tools/verify_release_jar.py dist/SkyVeLor-1.8.9-Beta-0.10.7v.jar --version Beta-0.10.7v
```

## Merge with the Beta-0.10.6.5v baseline

While this was being verified, PR #4 merged a new source baseline into `main` that
adds the Terminal GUI (`TerminalScreen`, `TerminalSolver`, `ClickInOrderHud`,
`DungeonHudScreen`, `TerminalCommand`) and an offline stub test rig, and that
removed the first-person files to match the archive it was imported from. Both lines
of work are kept: the Terminal GUI and its rig are unchanged, and the first-person
feature is restored on top.

Three things needed more than taking both sides:

- `PekaVersion.NAME` was **silently** taken from `main`. The merge base already read
  `Beta-0.10.7v`, so only one side looked modified and git resolved it to
  `Beta-0.10.6.5v` without reporting a conflict. `build.gradle` derives the archive
  name from that constant, so it would have produced
  `SkyVeLor-1.8.9-Beta-0.10.6.5v.jar` and skipped the intended release.
- `PekaClientMod` lost the `FirstPersonItemSetup` import while keeping both of its
  call sites, because `main`'s import block won the auto-merge. That does not
  compile.
- The workflow is a merge of both versions, and no longer hardcodes a version
  anywhere: it reads `PekaVersion.NAME`, so the jar name, the `dist/` path, the
  release tag and the verification all follow the source.

The figures in this document are from the merged tree, rebuilt and re-verified after
the merge.

## What is still untested

**The game was never launched.** No environment available here can run Minecraft
1.8.9 with a display, so there is no screenshot and no in-game confirmation. What is
proven is that the artifact is correctly built, correctly reobfuscated, and that the
overrides and setting reads are present in the shipped bytecode and bind to the right
vanilla members. What is not proven is what the held item looks like on screen.

Before publishing, check in Minecraft 1.8.9 with Forge `11.15.1.2318`:

- the log line `First-person item customization installed on EntityRenderer.<field>`
  appears once at startup, with no install warning after it;
- item scale changes the held item live at 50%, 100% and 200% for a sword, a tool, a
  block, a drawn bow and an empty hand;
- 100% looks identical to vanilla with the mod installed;
- animation speed changes how fast the item slides out and back when switching
  hotbar slots, without a jump or a stutter;
- the water, fire and pumpkin overlays, third person, and other players are
  unchanged;
- settings survive a restart from `skyvelor.properties`;
- the Terminal GUI, Click in order panel, existing HUDs, HUD editor, Spirit Leap,
  fishing and Slayer features all still work;
- behaviour on PojavLauncher/Android, which is a goal but has never been verified.

`EntityRenderer.itemRenderer` is `final`, so installing the renderer relies on
clearing that modifier through `java.lang.reflect`. That is a supported Java 8
technique and this project targets Java 8 exactly; it is not guaranteed to keep
working on a newer JVM.
